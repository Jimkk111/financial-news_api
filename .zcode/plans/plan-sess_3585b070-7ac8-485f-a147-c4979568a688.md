# 改进方案（修订版）：正文完整性修复 + 分类体系扩充

## 一、正文不完整——根因与修复

用户澄清：正文不是整体缺失，而是不完整、总缺一些内容。逐层核验抓取→清洗→结构化链路后，确认以下丢失路径（按影响排序）：

1. **清洗选择器子串误删正文节点（最系统性）**：`NewsIngestService.cleanContentHtml:293` 与 `ReadabilityExtractor.STRIP_SELECTOR:20-22` 用 `[class*=ad]`/`[id*=ad]` 做**子串**匹配，任何 class/id 含 "ad" 的正常节点都被删——`lazyload`、`upload`、`download`、`readmore`、`head`、`padding`、`shadow`、`thread`、`bread` 全命中，懒加载图片、图注、部分段落容器被静默移除。
2. **HTML→Block 转换丢裸文本**：`ContentCodec.parseElement` default 分支只递归子元素（`ContentCodec.java:210-222`），`<div>` 里夹在子元素之间的裸文本段整段丢失。
3. **表格行重复解析**：`el.select("tbody tr, tr")`（`ContentCodec.java:180`）逗号联合选择导致行重复，表格内容错乱。
4. **图片相对 URL 未绝对化**：img src 以 `/` 或 `//` 开头时前端裂图（connector 里 jsoup 带 baseUri，但直接取 `el.attr("src")` 不做 `absUrl` 归一）。
5. **东财长文分页**：列表只给 `xxx.html`，长文续页在 `xxx_2.html`，从不跟进（抽样 4 篇均短文单页，故按"检测到分页链接才跟进"的条件逻辑修，无分页零开销）。
6. **新浪 GBK 页面按 UTF-8 强解**（`CrawlHttpFetcher.java:48-50`）：正文乱码丢字。
7. **`news.content` 列为 TEXT（64KB）**（`init.sql:66`）：长文 HTML 超限时整篇入库失败。

### 改动 A（正文完整性）

- **A1 词元级广告清洗**：`cleanContentHtml` 与 `ReadabilityExtractor` 的 `[class*=ad]`/`[id*=ad]` 改为词元匹配——Java 侧拆 class/id 为 token，仅删除 token 等于 `ad`/`ads` 或以 `ad-`/`ad_` 开头的节点；`[class*=share]`/`[class*=recommend]` 同样收紧。新增小工具方法放 `ingest` 包内复用。
- **A2 ContentCodec 修复**：default 分支改为按 `childNodes` 顺序遍历（TextNode 与 Element 混排），裸文本非空即输出为 ParagraphBlock；表格解析改为只 select `tr`、首行按 `th`/`td` 判表头，消除重复行。
- **A3 东财分页跟进**：`EastmoneyConnector.fetchDetail` 检测正文区后的分页链接（`xxx_N.html` 模式 / `.pagination a`），依次抓取拼接 `contentHtml`，上限 10 页、复用现有按 host 限速。
- **A4 图片绝对化**：三个 Connector 在返回 `contentHtml` 前，对正文内 `img[src]` 用 `absUrl("src")` 归一（协议相对 `//` 补 `https:`）。
- **A5 编码检测**：`CrawlHttpFetcher.getString` 解码顺序改为 响应 Content-Type charset → HTML meta 嗅探（前 4KB）→ 严格 UTF-8 → GBK 兜底；方法签名不变，连接器零改动。
- **A6 列扩容**：`init.sql` 中 `news.content` TEXT→LONGTEXT（与 content_json 一致）；附存量库升级 SQL 到交付说明。
- **A7 门禁增强**：`QualityGate` 新增乱码率检测（U+FFFD 占比 >5% 拒绝，键 `crawler.ingest.max-mojibake-ratio`），防乱码文入库。
- **A8 摘要接通**：`ArticleRef` 加 `summaryHint`；sina 列表读 `intro`、华尔街见闻列表读 `content_short`（两者字段已实测存在），`fetchDetail` 透传，替代"一律取正文前 200 字"。

## 二、分类太少——根因与修复

根因（维持前次结论）：`categories` 表零种子数据；`AiTaggingService.java:107` prompt 强制只能从库中已有分类逐字选，白名单未命中即降级为 3 个 yml 兜底分类（国际财经/财经/股票）——死循环；未配 `AI_API_KEY` 时 AI 打标静默关闭；新建分类后 Redis 缓存 1 小时不失效。

### 改动 B（分类体系）

- **B1 种子分类 15 个**：宏观经济、货币政策、A股、港股、美股、全球市场、公司动态、产业经济、基金理财、债券、外汇、大宗商品、房地产、金融科技、综合财经（兜底）。`init.sql` 追加 `INSERT IGNORE`（新库）；新增 `config/CategorySeeder`（ApplicationRunner 幂等补种，覆盖已有 Docker 卷库），预置清单定义为 public 常量供 AI 打标复用。
- **B2 AI 受控新建**：`AiTaggingService` prompt 改为"优先从分类列表逐字选择，均不合适时可给 2~8 字新财经分类名"；`parseResult` 白名单未命中但通过格式校验（`[\u4e00-\u9fa5A-Za-z0-9]{2,8}`）则作为新分类返回，由现有 `findOrCreateCategory` 落库；库为空时以预置清单为候选不再放弃。
- **B3 缓存失效**：`NewsIngestService` 注入 `StringRedisTemplate`，真正新建分类/标签后删除 `cls:news:categories` / `cls:news:tags`（key 常量改为与 `NewsService` 共享的 public 常量）；Redis 操作 try-catch，不可用仅告警不阻断入库。
- **B4 yml 兜底对齐**：wallstreetcn→全球市场、sina→综合财经、eastmoney→A股（旧分类行保留，仅影响新数据兜底）。

## 三、存量回填（新端点）

`NewsIngestService.backfill(source?, limit)`：查 `content_json IS NULL OR CHAR_LENGTH(content) < 300` 的未软删记录（`NewsMapper` 新增 `selectBackfillCandidates`，publish_time 倒序、单批上限 100），按 `news.source` 匹配 `sourceName()` 找回连接器，按 URL 重抓 → 重走清洗/门禁/结构化 → 新增 `updateContent` 更新 content/content_json/summary/imageUrl，失败保留原值；每篇写 `crawl_audit`（reason 标注"回填"）。`CrawlerController` 新增 `POST /api/crawler/ingest/backfill`（沿用现有认证要求）。

## 不做的事

旧 LLM Agent 链路（`crawler.agent.*`，默认关闭）不动；不加分类管理 CRUD、不改 categories 表结构；iframe/视频嵌入仍按现状移除（转 VideoBlock 列为后续项）。

## 验证

1. `mvn clean package -DskipTests` 编译通过。
2. 本地触发 `POST /api/crawler/ingest`：抽样三源各 2 篇，将线上原文全文与库中 `content`/`content_json` 逐段比对，确认无丢段、无裂图、无乱码；`crawl_audit` 无异常 REJECTED 激增。
3. `GET /api/news/categories` 立即可见新分类（缓存失效生效）；连续采集后分类分布应超出 3 个。
4. 回填端点 `limit=5` 试跑，对比回填前后正文字数。
5. 交付说明附存量诊断 SQL（按 source 统计缺正文/疑似摘要型记录数）与 content 列升级 SQL。

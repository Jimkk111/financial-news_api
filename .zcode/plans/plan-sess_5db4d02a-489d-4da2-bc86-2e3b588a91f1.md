## 目标
在当前仓库中新增一个项目级 `project-context` 技能，让新会话优先读取一份短而可靠的项目上下文，而不是重复扫描整个代码库；同时支持初始化、按需刷新和针对当前任务的定向补充。

## 文件布局
1. 新建 `D:\workspace_2\financial-news_api\.agents\skills\project-context\SKILL.md`。
   - 使用合法 YAML frontmatter：`name: project-context`，description 明确覆盖“项目概览、技术栈、目录结构、运行/测试/部署、关键模块、约定、当前状态、熟悉陌生仓库、刷新上下文”等触发场景。
   - 技能正文保持精简，规定读取顺序、更新边界、输出格式和安全规则。
2. 在仓库根目录新建 `D:\workspace_2\financial-news_api\PROJECT_CONTEXT.md`，作为可提交、可被新会话快速读取的持久化事实摘要。
   - 采用稳定章节：项目定位与权威性、技术栈、目录/入口、运行测试部署、配置与依赖服务、API/业务模块、数据模型、爬虫架构、编码约定、当前 Git 状态/近期演进、已知差异与不确定项、来源文件与刷新信息。
   - 首次内容基于已确认的当前源码和配置，标明 HEAD/分支；不复制本地敏感配置。

## SKILL.md 行为设计
1. **先读后扫**：触发后先读取根目录 `PROJECT_CONTEXT.md`；存在且与当前提交/源码大体一致时，将其作为默认上下文，只针对用户问题读取少量源文件。
2. **初始化/刷新**：上下文不存在、用户明确要求初始化/刷新，或上下文记录的提交已落后时，按“权威源码和配置 > 当前部署文件 > 现有文档 > Git 历史”重新核验，并更新 `PROJECT_CONTEXT.md`。不把完整代码、日志或构建产物塞进摘要。
3. **通用探测清单**：根据仓库实际内容选择包管理文件、入口类、配置、容器编排、数据库 schema、控制器/路由、核心服务、测试目录和近期提交；不假定项目一定是 Java/Spring。
4. **定向阅读**：用户只问某模块时，先引用上下文，再读取该模块的实现和直接依赖；不要为了“完整”遍历 `target/`、`logs/`、`.idea/`、`node_modules/`、上传目录等噪声。
5. **事实与不确定性**：将“源码明确”“配置明确”“由工具约定推断”“文档可能过时”分开；命令没有被仓库明确记录时标注为推断。对当前仓库特别记录：无 README/CI/业务测试源码、crawler stream 实际同步返回、旧 crawler 文档与多 Agent 实现可能滞后等差异。
6. **秘密保护**：可读取配置键名和模板结构，但禁止把 API key、JWT secret、密码、邮箱凭据或 `application-dev.yml`/真实 `.env` 的值写入上下文或输出；必要时只写“已配置/未配置”和变量名。
7. **维护粒度**：只在初始化或明确刷新时写上下文文件；普通咨询只读，不因一次问答无依据地改文档。刷新后记录时间、分支和短 commit，保留来源路径，便于下次增量核验。
8. **面向用户的回答**：先给结论，再给与任务相关的最小上下文；若执行了刷新，说明更新了哪些章节；引用仓库文件路径和行号，不输出大段文件转储。
9. **示例格式**：在技能中放置一个简短的上下文条目示例，展示“事实 / 推断 / 需核实”标签以及脱敏配置写法，帮助后续会话稳定遵循格式。

## 验证步骤
1. 检查 frontmatter、目录名/技能名、Markdown 章节和敏感值扫描；确认新增文件可被 `.agents/skills` 发现且没有改动其他文件。
2. 用 2–3 个真实提示验证技能行为（按 skill-creator 流程在新鲜调用中测试）：
   - “初始化这个仓库的项目上下文，告诉我技术栈、运行方式和关键入口。”
   - “我要修改爬虫来源，先基于项目上下文指出相关模块和测试命令，不要遍历整个仓库。”
   - “刷新项目上下文，检查最近提交是否改变了爬虫架构，并标出过时文档。”
3. 验证结果应体现：优先读取 `PROJECT_CONTEXT.md`、只定向核验、明确不确定项、无密钥泄露；若测试暴露重复扫描或上下文过长，再收紧技能正文和摘要章节。
